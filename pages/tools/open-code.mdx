# OpenCode

**Made by:** Community / SST
**Type:** Open-Source Terminal Coding Agent
**Best for:** Developers who want full control, local-first workflows, scripting and automation

<ConceptVideo id="tool-open-code" title="OpenCode: open-source coding agents" />

## What it is

OpenCode is an open-source terminal-based coding agent — the community answer to Claude Code and Codex CLI. It runs in your terminal, reads your codebase, and executes coding tasks using whichever AI model you connect to it.

Because it's open source, you can:
- Self-host it entirely (no data leaving your network)
- Connect your own models (local LLMs, private deployments)
- Script and automate it however you like
- Audit exactly what it's doing
- Extend it with custom tools for your internal systems

## Why it matters

Most coding assistants are proprietary — your code goes to someone else's server. For organisations with strict data policies, on-premise requirements, or air-gapped environments, OpenCode is often the only viable choice.

It also serves developers who simply want ownership over their tools: the ability to read the source, contribute, and extend without waiting for a vendor.

## Quick start

<Steps>

### Install OpenCode

```bash
npm install -g opencode-ai
# or with the install script
curl -fsSL https://opencode.ai/install | bash
```

### Configure your model

```bash
# Use Claude (recommended for best results)
opencode config set model claude-sonnet-4-5
opencode config set api_key YOUR_ANTHROPIC_KEY

# Or use a local model via Ollama (fully private)
opencode config set model ollama/codellama:13b
opencode config set base_url http://localhost:11434
```

### Run in your project

```bash
cd my-project
opencode
```

### Give it a task

```
> Refactor the database layer to use connection pooling
```

OpenCode will read the relevant files, plan the changes, show you the diff, and apply them when you approve.

</Steps>

## Core features

**Model-agnostic** — Works with Claude, GPT-4, Gemini, Mistral, or a locally-running Ollama model. Switch models with a single config change.

**Terminal-native** — No GUI, no Electron app. Runs wherever a shell runs — local machine, SSH session, Docker container, CI runner.

**File-system tools** — Reads files, writes files, creates directories, runs shell commands. The same tool loop as Claude Code but open and configurable.

**Scriptable** — Pass tasks via stdin or arguments for fully automated pipelines:
```bash
echo "Add input validation to POST /users" | opencode --model claude-sonnet-4-5
```

**Plugin system** — Add custom tools (database queries, internal APIs, company-specific linters) without forking the project.

## Configuration

OpenCode is configured via `~/.config/opencode/config.json` or a `.opencode.json` in your project root:

```json
{
  "model": "claude-sonnet-4-5",
  "provider": "anthropic",
  "api_key": "${ANTHROPIC_API_KEY}",
  "auto_approve": false,
  "context_files": [".opencode-context.md"],
  "tools": {
    "shell": true,
    "browser": false,
    "custom": ["./tools/internal-api.js"]
  },
  "rules": [
    "Always write tests for new functions",
    "Follow the existing code style",
    "Never modify migration files"
  ]
}
```

### Project-level context

Create a `.opencode-context.md` file in your project root to give OpenCode knowledge about your codebase:

```markdown
# Project Context

## Architecture
- Backend: Node.js + Express, PostgreSQL via Prisma
- Frontend: React + Vite, Tailwind CSS
- Auth: JWT tokens, refresh token rotation

## Conventions
- Database models in /src/models
- API routes in /src/routes, one file per resource
- Tests in /tests, mirror the src structure

## Do not touch
- /migrations — never edit migration files directly
- /src/legacy — deprecated code being phased out

## Key abstractions
- `withAuth(handler)` — middleware wrapping for protected routes
- `db.transaction(fn)` — use for any multi-table writes
```

## Using local models

For fully offline or private operation:

```bash
# Install Ollama
curl -fsSL https://ollama.ai/install.sh | sh

# Pull a code model
ollama pull codellama:13b
# Or for better quality at the cost of speed:
ollama pull deepseek-coder:33b

# Configure OpenCode to use it
opencode config set model ollama/codellama:13b
opencode config set base_url http://localhost:11434/v1
```

<Callout type="warning">
Local models are significantly less capable than frontier models like Claude Sonnet for complex multi-file tasks. Use them when privacy requirements are strict and accept the quality tradeoff. For most tasks involving more than 3-4 files, a frontier model will save you far more time than the privacy cost.
</Callout>

## Scripting and automation

OpenCode shines in automated pipelines. Some useful patterns:

### CI/CD code review

```bash
# In your CI pipeline, run OpenCode on changed files
git diff origin/main...HEAD --name-only | xargs opencode review \
  --model claude-haiku-4-5 \
  --output review.md \
  --prompt "Review these changes for security issues, missing error handling, and test coverage gaps"
```

### Batch refactoring

```bash
# Apply the same change across many files
for file in src/api/*.ts; do
  opencode --file "$file" \
    --prompt "Add JSDoc comments to all exported functions" \
    --auto-approve
done
```

### Automated test generation

```bash
# Generate tests for untested functions
opencode --prompt "Look at src/utils/pricing.ts and write comprehensive unit tests. Save them to tests/utils/pricing.test.ts" \
  --auto-approve
```

## Custom tools / plugins

Extend OpenCode with tools that talk to your internal systems:

```javascript
// tools/jira.js
module.exports = {
  name: "create_jira_ticket",
  description: "Create a Jira ticket for a bug or task",
  parameters: {
    type: "object",
    properties: {
      summary: { type: "string" },
      description: { type: "string" },
      priority: { type: "string", enum: ["Low", "Medium", "High", "Critical"] }
    },
    required: ["summary", "description"]
  },
  async execute({ summary, description, priority = "Medium" }) {
    const response = await fetch(`${process.env.JIRA_URL}/rest/api/3/issue`, {
      method: "POST",
      headers: {
        "Authorization": `Basic ${Buffer.from(`${process.env.JIRA_USER}:${process.env.JIRA_TOKEN}`).toString('base64')}`,
        "Content-Type": "application/json"
      },
      body: JSON.stringify({
        fields: {
          project: { key: process.env.JIRA_PROJECT },
          summary,
          description: { type: "doc", version: 1, content: [{ type: "paragraph", content: [{ type: "text", text: description }] }] },
          issuetype: { name: "Bug" },
          priority: { name: priority }
        }
      })
    });
    const ticket = await response.json();
    return `Created ticket: ${ticket.key} — ${process.env.JIRA_URL}/browse/${ticket.key}`;
  }
};
```

Register it in `.opencode.json`:

```json
{
  "tools": {
    "custom": ["./tools/jira.js"]
  }
}
```

Now the agent can create Jira tickets as part of its workflow.

## OpenCode vs Claude Code

| | OpenCode | Claude Code |
|---|---|---|
| Open source | Yes | No |
| Self-hostable | Yes | No |
| Local models | Yes | No |
| Model quality (default) | Depends on your choice | Claude (Anthropic's best) |
| Custom tools/plugins | Yes | Limited |
| Maintenance | Community | Anthropic |
| Enterprise support | Community forums | Anthropic support |
| Agent SDK integration | Via plugins | Native |

## Best use cases

- Teams with **strict data sovereignty** requirements
- Developers building **automated pipelines** that call a coding agent programmatically
- Organisations running **air-gapped** environments
- Developers who want to **extend and customise** their coding agent with internal tools
- Engineers comfortable on the command line who don't want or need a GUI
- Teams that want to **audit** exactly what the agent does to their code
