# Recipe: SRE Watchdog

**Department:** Platform Engineering / DevOps
**Difficulty:** Intermediate
**Time to set up:** 1–2 hours

<ConceptVideo id="recipe-sre-watchdog" title="A 24/7 agent that monitors infrastructure, auto-remediates issues, and alerts you when humans need to step in" />

## Overview

The SRE Watchdog agent runs 24/7, continuously monitoring your Kubernetes cluster and services. It detects crashes, resource pressure, and service degradation — fixes what it can silently, and alerts you only when human intervention is needed. The result is faster incident response, fewer 3am pages, and infrastructure that largely maintains itself.

## Use Case

**Who this is for:** Platform engineers, DevOps teams, and solo founders running production infrastructure who are tired of being the only one awake at 3am when a pod crashes.

**The problem it solves:** Infrastructure monitoring requires constant attention — pod crashes, disk filling up, services degrading, error logs piling up. Traditional alerting systems wake you up for everything, including things that could have been auto-fixed. Manual toil consumes engineering time that should go toward building, not babysitting.

**Trigger:** A heartbeat that runs every 5 minutes (configurable), checking cluster health and service endpoints.

## Agent Architecture

| Component | Purpose |
|---|---|
| Kubernetes (kubectl) | Monitors pod health, crash loops, PVCs, node resources |
| Messaging (Telegram, Slack) | Sends alerts and remediation summaries |
| Model provider (Ollama, OpenRouter) | Powers the agent's reasoning and decision-making |
| Playbooks (memory) | Defines remediation steps for common failure patterns |
| Heartbeat scheduler | Runs health checks on a configurable interval |
| Persistent storage (PVC) | Keeps state, logs, and playbooks across restarts |

This recipe uses a **heartbeat-driven orchestration pattern**: the agent wakes up every few minutes, runs a checklist, compares results against known state, and only acts or alerts when something changed.

### Set up the OpenClaw configuration

Create an `openclaw.json` configuration file. This is the main config that defines your agent's model, messaging channel, tools, and heartbeat interval.

Key settings:
- **Model:** Use a cloud model like `glm-5.1:cloud` on Ollama or `z-ai/glm-5.1` on OpenRouter for reliable 24/7 availability
- **Heartbeat interval:** `300` seconds (5 minutes) — frequent enough to catch issues, sparse enough to keep costs low
- **Exec security:** `full` — the agent needs shell access to run `kubectl` and diagnostic commands
- **Channel:** Telegram or Slack for alerts

### Write the agent's personality

Create a `SOUL.md` file in the workspace. This defines how the agent thinks and communicates.

The SRE Watchdog should be terse, action-oriented, and prefer fixing things silently over waking you up at 3am.

```markdown
# SRE Watchdog

You are an always-on Site Reliability Engineer. Your job: keep infrastructure healthy, detect problems early, and fix what you can silently.

## Principles

- **Prefer auto-remediation** over alerts. Fix it, then tell the human what you fixed.
- **Be concise in alerts.** Include: what broke, what you did, what to check. No fluff.
- **Don't over-alert.** If you restarted a pod at 3am and it came back fine, leave a note, not a page.
- **Know your limits.** Never delete production data, rotate certs, or change security policy without explicit approval.
- **Document everything.** Write remediation actions to memory/daily notes with timestamps.
- **Stay calm.** Infrastructure breaks. That's normal. Fix it methodically.

## Tone

Short, technical, precise. You're a pager-duty responder, not a chatbot.
```

### Define the heartbeat checklist

Create a `HEARTBEAT.md` file. This is the script the agent follows every time it wakes up.

```markdown
# SRE Watchdog Heartbeat

## Every 5 minutes — Infrastructure Health

### Kubernetes
- Check pod health: `kubectl get pods -A --field-selector=status.phase!=Running`
- Check crash loops: `kubectl get pods -A | grep -E 'CrashLoop|Error|OOMKilled'`
- Check PVCs: `kubectl get pvc -A`
- If issues found → diagnose, attempt auto-remediation, alert owner

### Service Health
- Probe critical endpoints (gateway health, API health)
- Check response times and error rates
- If degradation detected → investigate logs, restart if needed

### Disk & Resources
- Check node disk usage: `df -h`
- Check memory pressure: `kubectl top nodes` (if metrics-server available)
- If >85% disk → clean up logs, alert owner

### Log Analysis
- Recent errors: `kubectl logs -l app=<service> --tail=50` for each critical service
- Pattern detection: recurring errors, new error types
- If new critical errors → investigate, attempt fix, alert

## Escalation Rules

- **Silent fix**: Restart a crashed pod, clear temp files, retry failed deploys
- **Alert owner**: Disk >90%, repeated OOM kills, service down >5 min, security anomalies
- **Never act on**: Production data deletion, force-push main branch, cert rotation
- **Quiet hours (23:00-07:00)**: Only alert for P0 incidents (service down, security breach)

## State Tracking

Write results to `memory/heartbeat-state.json`:
```json
{
  "lastChecks": {
    "pods": 1747579200,
    "endpoints": 1747579200,
    "disk": 1747578900,
    "logs": 1747579200
  },
  "knownIssues": [],
  "silencedAlerts": []
}
```

Do NOT repeat alerts for known issues that are already tracked.
```

### Write remediation playbooks

Create playbook files under `memory/playbooks/` in the agent workspace. These give the agent specific steps for common failure scenarios.

**`memory/playbooks/pod-crashloop.md`:**

```markdown
# Playbook: Pod CrashLoopBackOff

1. `kubectl logs <pod> -n <ns> --tail=100` — get recent logs
2. `kubectl describe pod <pod> -n <ns>` — check events
3. Common fixes:
   - OOMKilled → increase memory limits
   - Config error → check secrets/configmaps
   - Failed probe → check if service actually started
4. If transient: `kubectl delete pod <pod> -n <ns>` (let it restart)
5. If persistent: alert owner with logs summary
```

**`memory/playbooks/service-down.md`:**

```markdown
# Playbook: Service Down

1. `kubectl get pods -n <ns> -l app=<service>` — check pod status
2. `kubectl logs -l app=<service> -n <ns> --tail=50` — check logs
3. Check endpoints: `kubectl get endpoints <service> -n <ns>`
4. If no pods running: check deployment events
5. If crash loop: follow pod-crashloop playbook
6. If pods running but unhealthy: check readiness probes
7. Auto-remediation: restart deployment if no config change needed
8. Alert owner with: service name, status, action taken, logs snippet
```

**`memory/playbooks/disk-full.md`:**

```markdown
# Playbook: Disk Full

1. `df -h` — find full partition
2. `du -sh /var/log/* | sort -rh | head -10` — find large logs
3. Safe cleanups:
   - Old logs: `find /var/log -name "*.log" -mtime +7 -delete`
   - Docker: `docker system prune -f` (if available)
   - K8s: `kubectl delete pods --field-selector=status.phase=Failed -A`
4. If still >85%: alert owner
```

### Deploy to Kubernetes

Create a Kubernetes manifest with a Secret for configuration and a Deployment for the agent.

Key deployment details:
- **Persistent storage:** Use a PVC so state, playbooks, and memory survive restarts
- **Probes:** Health/readiness probes at `/healthz` and `/readyz` ensure K8s restarts the agent if it becomes unresponsive
- **Init container:** Merges config from the Secret with any runtime state on the PVC
- **Resource limits:** 1Gi request / 4Gi limit — enough for model inference

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: sre-watchdog-config
  namespace: claws-runtime
type: Opaque
stringData:
  openclaw.json: |
    <paste your openclaw.json here>
  OLLAMA_API_KEY: "<OLLAMA_KEY>"
  OPENCLAW_GATEWAY_TOKEN: "<GATEWAY_TOKEN>"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sre-watchdog
  namespace: claws-runtime
  labels:
    app: openclaw
    claws.io/claw-id: sre-watchdog
spec:
  replicas: 1
  selector:
    matchLabels:
      app: openclaw
      claws.io/claw-id: sre-watchdog
  strategy:
    type: Recreate
  template:
    metadata:
      labels:
        app: openclaw
        claws.io/claw-id: sre-watchdog
    spec:
      securityContext:
        fsGroup: 1000
        fsGroupChangePolicy: "OnRootMismatch"
      containers:
        - name: openclaw
          image: ghcr.io/openclaw/openclaw:latest
          imagePullPolicy: IfNotPresent
          env:
            - name: OLLAMA_API_KEY
              valueFrom:
                secretKeyRef:
                  name: sre-watchdog-config
                  key: OLLAMA_API_KEY
            - name: OPENCLAW_GATEWAY_TOKEN
              valueFrom:
                secretKeyRef:
                  name: sre-watchdog-config
                  key: OPENCLAW_GATEWAY_TOKEN
          livenessProbe:
            httpGet: { path: /healthz, port: http }
            initialDelaySeconds: 120
            periodSeconds: 10
            failureThreshold: 6
          readinessProbe:
            httpGet: { path: /readyz, port: http }
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 24
          startupProbe:
            httpGet: { path: /healthz, port: http }
            periodSeconds: 5
            failureThreshold: 72
          ports:
            - name: http
              containerPort: 18789
          resources:
            requests: { memory: "1Gi" }
            limits: { memory: "4Gi" }
          volumeMounts:
            - name: home
              mountPath: /home/node/.openclaw
      volumes:
        - name: home
          persistentVolumeClaim:
            claimName: sre-watchdog-home
        - name: config
          secret:
            secretName: sre-watchdog-config
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: sre-watchdog-home
  namespace: claws-runtime
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 5Gi
```

Deploy with:

```bash
kubectl apply -f sre-watchdog.yaml
kubectl get pods -n claws-runtime -w
```

### Verify it's running

Once the pod is `1/1 Running`, message your Telegram bot to confirm it responds. Then watch the logs for heartbeat activity:

```bash
kubectl logs -n claws-runtime -l claws.io/claw-id=sre-watchdog --tail=20
```

You should see:
- `[gateway] agent model: ollama/glm-5.1:cloud`
- `[heartbeat] started`
- `[telegram] [default] starting provider`

The agent will begin its first heartbeat check within 5 minutes.

## Tips & Variations

**Multi-cluster monitoring:** Point `kubectl` at different clusters using `KUBECONFIG` context switching. Add a cluster field to your heartbeat state so the agent tracks which cluster it's checking.

**Slack integration:** Add a Slack channel alongside Telegram for team-wide visibility. Alert messages go to both channels; auto-remediation notes go to Slack only (no need to wake someone up for a fix already applied).

**Escalation tiers:** Add a second heartbeat that runs every 30 minutes for deeper checks — log pattern analysis, certificate expiry warnings, and drift detection. Use a cheaper model for the 30-min tier to keep costs down.

**Webhook probes:** Extend the heartbeat to `curl` your public endpoints and API health routes. The agent can detect 5xx responses and correlate them with pod restarts.

**Cost optimization:** Use a free/cheap model for the heartbeat tier (the agent is mostly running `kubectl` commands, not reasoning) and only invoke the primary model when an anomaly is detected. Set `heartbeat.model` to `"openrouter/free"` for the health check loop.

## Getting Started

1. **Create a Telegram bot** — message @BotFather on Telegram, run `/newbot`, and save the token. Message @userinfobot to get your Telegram user ID.
2. **Generate a gateway token** — run `openssl rand -hex 16` and save it. This authenticates the agent.
3. **Get a model API key** — sign up at ollama.com (free tier available) or openrouter.ai for your inference provider.
4. **Fill in the config** — replace all `<PLACEHOLDER>` values in `openclaw.json` with your real tokens and IDs.
5. **Deploy to Kubernetes** — `kubectl apply -f sre-watchdog.yaml` and watch the pod come up.
6. **Message the bot** — send any message on Telegram to confirm the agent responds.
7. **Wait for the first heartbeat** — within 5 minutes, check the logs for your first health check results. The agent will alert you if anything is wrong, or stay quiet if everything is healthy.
