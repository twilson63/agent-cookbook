Your infrastructure breaks at 3am. You wake up to a pager alert, log in, restart a pod, and go back to sleep. Tomorrow night, it happens again. The fix is always the same — but you're the one doing it.

What if an agent could handle this? Not a fancy ML monitoring platform with a per-seat license. Just an OpenClaw agent that runs `kubectl` commands every 5 minutes, fixes what it can, and only wakes you up when it can't.

I set one up this week. Here's how.

## What It Does

The SRE watchdog agent:

- **Wakes up every 5 minutes** and runs a health check across your Kubernetes cluster
- **Auto-remediates** common issues — restarting crashed pods, cleaning up disk space, retrying failed deployments
- **Alerts you** only when it can't fix something, or when something looks genuinely dangerous (OOM kills, security anomalies, disk >90%)
- **Stays quiet** during resolved incidents — it tracks state so it doesn't page you about the same problem twice
- **Documents everything** — every action it takes goes into daily memory files with timestamps

The key insight: most "incidents" are repetitive and fixable. The agent handles 80-90% of them silently. You only hear about the ones that actually need a human.

## The Architecture

It's one OpenClaw agent running on a pod in your cluster with three workspace files:

1. **`SOUL.md`** — who the agent is and how it thinks
2. **`HEARTBEAT.md`** — the checklist it follows every 5 minutes
3. **`memory/playbooks/`** — specific remediation steps for common failures

The heartbeat is the engine. Every 5 minutes, the agent reads `HEARTBEAT.md`, runs the checks, takes action, and writes results to `memory/heartbeat-state.json`. If something needs your attention, it sends you a Telegram message.

## Step 2: Write the Agent's Brain

Create `SOUL.md`:

```markdown
# SRE Watchdog

You are an always-on Site Reliability Engineer. Your job: keep infrastructure healthy, detect problems early, and fix what you can silently.

## Principles

- **Prefer auto-remediation** over alerts. Fix it, then tell the human what you fixed.
- **Be concise in alerts.** What broke, what you did, what to check. No fluff.
- **Don't over-alert.** If you restarted a pod at 3am and it came back fine, leave a note, not a page.
- **Know your limits.** Never delete production data, rotate certs, or change security policy without explicit approval.
- **Document everything.** Write remediation actions to memory with timestamps.
- **Stay calm.** Infrastructure breaks. That's normal. Fix it methodically.

## Tone

Short, technical, precise. You're a pager-duty responder, not a chatbot.
```

## Step 3: Write the Heartbeat Checklist

Create `HEARTBEAT.md`:

```markdown
# SRE Watchdog Heartbeat

## Every 5 minutes — Infrastructure Health

### Kubernetes
- Check pod health: `kubectl get pods -A --field-selector=status.phase!=Running`
- Check crash loops: `kubectl get pods -A | grep -E 'CrashLoop|Error|OOMKilled'`
- Check PVCs: `kubectl get pvc -A`
- If issues found → diagnose, attempt auto-remediation, alert owner

### Service Health
- Probe critical endpoints (gateway health, API health)
- Check response times and error rates
- If degradation detected → investigate logs, restart if needed

### Disk & Resources
- Check node disk usage: `df -h`
- If >85% disk → clean up logs, alert owner

### Log Analysis
- Recent errors: `kubectl logs -l app=<service> --tail=50`
- If new critical errors → investigate, attempt fix, alert

## Escalation Rules

- **Silent fix**: Restart a crashed pod, clear temp files, retry failed deploys
- **Alert owner**: Disk >90%, repeated OOM kills, service down >5 min, security anomalies
- **Never act on**: Production data deletion, force-push main branch, cert rotation
- **Quiet hours (23:00-07:00)**: Only alert for P0 incidents

## State Tracking

Write results to `memory/heartbeat-state.json`. Do NOT repeat alerts for known issues.
```

## Step 4: Write Playbooks

Create `memory/playbooks/pod-crashloop.md`:

```markdown
# Playbook: Pod CrashLoopBackOff

1. `kubectl logs <pod> -n <ns> --tail=100` — get recent logs
2. `kubectl describe pod <pod> -n <ns>` — check events
3. Common fixes:
   - OOMKilled → increase memory limits
   - Config error → check secrets/configmaps
   - Failed probe → check if service actually started
4. If transient: `kubectl delete pod <pod> -n <ns>` (let it restart)
5. If persistent: alert owner with logs summary
```

Create `memory/playbooks/service-down.md`:

```markdown
# Playbook: Service Down

1. `kubectl get pods -n <ns> -l app=<service>` — check pod status
2. `kubectl logs -l app=<service> -n <ns> --tail=50` — check logs
3. Check endpoints: `kubectl get endpoints <service> -n <ns>`
4. If no pods running: check deployment events
5. If crash loop: follow pod-crashloop playbook
6. Auto-remediation: restart deployment if no config change needed
7. Alert owner with: service name, status, action taken, logs snippet
```

Create `memory/playbooks/disk-full.md`:

```markdown
# Playbook: Disk Full

1. `df -h` — find full partition
2. `du -sh /var/log/* | sort -rh | head -10` — find large logs
3. Safe cleanups:
   - Old logs: `find /var/log -name "*.log" -mtime +7 -delete`
   - K8s: `kubectl delete pods --field-selector=status.phase=Failed -A`
4. If still >85%: alert owner
```

Key settings:
- **`heartbeat.interval: 300`** — wakes up every 5 minutes (adjust to 60 for aggressive, 900 for chill)

- **`elevatedDefault: "full"` — allows the agent to act on elevated commands without asking

## Step 6: Deploy to Kubernetes

Create `sre-watchdog.yaml`:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: sre-watchdog-config
  namespace: claws-runtime
type: Opaque
stringData:
  openclaw.json: |
    <paste your openclaw.json here>
  OLLAMA_API_KEY: "<YOUR_OLLAMA_KEY>"
  OPENCLAW_GATEWAY_TOKEN: "<GATEWAY_TOKEN>"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sre-watchdog
  namespace: claws-runtime
  labels:
    app: openclaw
    claws.io/claw-id: sre-watchdog
spec:
  replicas: 1
  selector:
    matchLabels:
      app: openclaw
      claws.io/claw-id: sre-watchdog
  strategy:
    type: Recreate
  template:
    metadata:
      labels:
        app: openclaw
        claws.io/claw-id: sre-watchdog
    spec:
      securityContext:
        fsGroup: 1000
        fsGroupChangePolicy: "OnRootMismatch"
      containers:
        - name: openclaw
          image: ghcr.io/openclaw/openclaw:latest
          env:
            - name: OLLAMA_API_KEY
              valueFrom:
                secretKeyRef:
                  name: sre-watchdog-config
                  key: OLLAMA_API_KEY
            - name: OPENCLAW_GATEWAY_TOKEN
              valueFrom:
                secretKeyRef:
                  name: sre-watchdog-config
                  key: OPENCLAW_GATEWAY_TOKEN
          livenessProbe:
            httpGet: { path: /healthz, port: http }
            initialDelaySeconds: 120
            periodSeconds: 10
            failureThreshold: 6
          readinessProbe:
            httpGet: { path: /readyz, port: http }
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 24
          startupProbe:
            httpGet: { path: /healthz, port: http }
            periodSeconds: 5
            failureThreshold: 72
          ports:
            - name: http
              containerPort: 18789
          resources:
            requests: { memory: "1Gi" }
            limits: { memory: "4Gi" }
          volumeMounts:
            - name: home
              mountPath: /home/node/.openclaw
      volumes:
        - name: home
          persistentVolumeClaim:
            claimName: sre-watchdog-home
        - name: config
          secret:
            secretName: sre-watchdog-config
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: sre-watchdog-home
  namespace: claws-runtime
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 5Gi
```

Deploy it:

```bash
kubectl apply -f sre-watchdog.yaml
kubectl get pods -n claws-runtime -w
```

Wait for `1/1 Running`. Then message your Telegram bot to confirm it responds.

```bash

You should see:
```

[heartbeat] started

Within 5 minutes, the agent will run its first health check. If everything is green, it stays quiet. If something's wrong, you'll get a Telegram message with a summary.

## What Happens in Practice

**Scenario 1: Pod crashes at 3am**

The heartbeat detects `CrashLoopBackOff`. The agent reads the pod's logs, identifies the cause (let's say an OOM kill), deletes the pod to force a restart, and logs the action. Pod comes back. You wake up to a Telegram message: *"Pod api-server-7f8d9 in production namespace crashed (OOMKilled). Deleted pod to force restart. Pod is now Running. Memory limit may need adjustment."*

**Scenario 2: Disk filling up**

The agent sees node disk at 87%. It runs the disk-full playbook — finds 2GB of old logs, cleans them up, rechecks. Disk drops to 72%. No alert needed. The next morning you see a note in memory: *"Cleaned 2GB of logs from node-1. Disk at 72%."*

**Scenario 3: Service genuinely down**

The agent can't restart a service because the deployment itself has a bad config. It tries once, fails, and sends you a message: *"Service payment-api is down. Attempted restart — pods not coming up. Last error: ConfigMap 'payment-config' references missing key. Check your deployment."* Now you're not starting from scratch — you already know what's wrong.

## Cost Optimization

The heartbeat model runs every 5 minutes but it's mostly executing shell commands. Use `"openrouter/free"` for the heartbeat model — it only needs to read the output and decide whether to act. The primary model (`glm-5.1:cloud` on Ollama) only fires when there's an actual issue to diagnose or an alert to compose.

At 5-minute intervals with free-tier heartbeat model, you're looking at roughly $0.02-0.05/day on Ollama for the primary model calls (only triggered when something breaks). Compare that to a $20-50/month monitoring SaaS.

## Making It Yours

**Add your services:** Edit `HEARTBEAT.md` to add service-specific checks:

```markdown
### Payment API
- Probe: `curl -sf https://api.example.com/health || echo DOWN`
- Pods: `kubectl get pods -n production -l app=payment-api`
- If down → restart deployment, alert owner
```

**Add Slack alongside Telegram:** Drop a Slack channel config into `openclaw.json` for team visibility. Auto-remediation notes go to Slack; only P0 pages go to Telegram.

**Tune the escalation:** Adjust the quiet hours and thresholds to match your team's on-call schedule. The playbooks are plain markdown — edit them anytime, the agent picks up changes on the next heartbeat.
